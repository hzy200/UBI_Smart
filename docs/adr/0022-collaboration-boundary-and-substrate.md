# ADR-0022：协作开发止步于 sandbox 侧，host 侧只用 Git 交换代码

- **Status**：proposed
- **Date**：2026-10-28
- **Deciders**：项目作者
- **Owner**：项目作者

## Context

企业部署形态下，A2/A3/A4 在服务器，A1 与 A2L 在客户端（ADR-0015）。
工作区有两种形态：`host` 的字节在用户 NTFS、由 A2L 保管；`sandbox` 的字节在
服务器 ext4、由 A4 保管。默认值是「客户端新工作区 `host`，服务端/CI `sandbox`」。

于是企业里最常见的实际形态是：**代码与编译环境都在每个人自己的机器上，
服务器只做认证、调度、计量与上游密钥托管。** 唯一被集中共享的是控制面资源
——上游 Key（AES-256-GCM 密文）、每日配额与用量。

问题：能否支持"企业协作开发"——多人同一仓库、统一编译环境、互相评审。

约束（写清当时的处境）：

- A2L **只主动外连、不开入站**；服务端请求不等于授权；本地 grant/ZX 是最终
  闸门；企业设备用证书指纹做预登记与吊销。
- `sandbox` 工作区**必须放 ext4**，禁止在工具热路径上跨 `/mnt`（第 12.1、14 节）。
  SMB/Windows 共享目录不可行；NFS/Ceph 只在 Linux 基线成立；Windows 基线的
  ext4 在 WSL2 VHDX 里，跨机共享不成立。
- 控制面 MySQL **不存**工作区文件、checkpoint、运行状态（第 13 节）。
- 并发是单进程共享 governor：WSL 槽位 + LLM 全局并发上限。多人同时跑是容量
  问题，不是协作问题。
- 审计按租户单写者，A3 本地哈希链是可信源，A2 只建索引。

可选方案：

1. 工作区搬进共享存储，多人同一棵文件树（NFS/SMB/对象存储）；
2. `host` 工作区跨人共享（B 发起的 run 打到 A 的机器上执行）；
3. `sandbox` 为中心：工作区在服务器 ext4，按工作区成员制授权；
4. 不提供协作，只保留 Git 交换代码；
5. 云化重建（多租户 SaaS）。

## Decision

### 一、边界判定（描述现状，即日生效）

**当前架构下不存在真正的协作开发，只有「每个人各自用 AI + 用 git 交换代码」。
这不是缺陷，是安全边界的必然结果。**

判据：**共享成本随资源离开控制面的距离上升。**

| 层 | 资源 | 谁持有 | 共享成本 |
|---|---|---|---|
| 控制面 | 上游 Key、配额、计量、审计索引 | A2 / MySQL | 已共享，无文件系统耦合 |
| 执行面（服务器） | `sandbox` 工作区、构建环境、快照 | A4 / 服务器 ext4 | 可改造：成员制授权 + 路径迁移 |
| 执行面（客户端） | `host` 工作区、本机工具链、本地 grant | A2L / 用户 NTFS | **不可共享**：撞 A2L 信任模型 |

`host` 之所以"不能"而不是"还没"，是因为跨人共享等于把 A 的机器变成 B 的执行
节点，会逐条推翻 ADR-0015 的四条约束：只外连、本地同意、服务端请求不等于
授权、设备证书绑定。**这一层隔离是刻意设计，不是待补的缺口。**

### 二、协作基座二选一（待定，本轮不实施）

要真做协作，必须先选定唯一的基座，不允许"两边都能改"：

- **选 `sandbox`**：可共享工作区、构建环境、上下文、审计与配额。代价是源码
  上服务器（需过安全评审）、需要 ext4 共享存储或单机、`allow_git_clone`
  默认 `False` 要先解决入库路径。
- **选 `host`**：只能靠 Git 交换代码；编译环境永不统一；跨机审计无法拼成完整链。

**推荐以 `sandbox` 为主线，`host` 保留给个人与离线场景，两者不跨挂载。**

### 三、明确不做的事

- **不做**共享可写文件树：ADR-0013 已否决 SMB/NFS/对象存储作为执行热路径，
  且与 ext4 强制冲突。
- **不做**跨人 `host` 执行：会把客户端变成他人的执行节点，等于给横向移动开通道。
- **不做**云化重建：云化的门槛在执行后端（WSL 无法在 Linux 容器内运行，
  要切 bwrap 并重做隔离语义），不在协作功能；两件事并行会互相拖累。
- **不把"只有 Git 交换"包装成协作功能对外承诺**，它只是当前边界下的可用手段。

否决理由：方案 1 的 POSIX 语义、锁与性能问题在 ADR-0013 已论证过；方案 2 推翻
A2L 信任模型；方案 3 之外的"两条都支持"会让审计与路径语义分叉，属于最难维护
的中间态；方案 5 的代价被低估（换执行后端是项目级改造，不是加功能）。

## Consequences

### 好的

- 边界写死，避免做出"半个协作功能"：既不会有人误以为已支持多人同仓，
  也不会有人去开跨人 `host` 执行的口子。
- 后续改进只需在 `sandbox` 侧收敛，`host` 侧一行不用碰，范围直接减半。
- 与 ADR-0013 / 0015 / 0004 的假设一致，不引入新的信任假设。

### 坏的 / 代价

- 企业若坚持"源码不出本机"，就真的没有协作开发。这是产品能力的硬缺口，
  方案评审与销售时必须明说，不能含糊。
- `host` 模式下审计跨机器不可拼：每人一条本地哈希链，A2 只有索引，
  "某次改动是谁做的"在不同机器之间无法形成完整叙述。
- 编译环境漂移在 `host` 模式下无法用工具解决，只能靠流程约定。
- 一旦选定 `sandbox`，源码上服务器会触发安全评审，这一步常常比技术改造更慢。

### 中性 / 需要留意

- "共享编译环境"在 `sandbox` 模式下本来就成立（同一 WSL 发行版 / 同一台
  Linux 主机），但会把"环境漂移"换成"环境互踩"，需要版本化的工具链快照，
  而不是简单共用一份。
- 会话共享（旁观 / 接管）只涉及事件 key 与 SSE 鉴权，不触碰工作区归属，
  可以作为独立小项先做；但它**不构成**协作开发，别把它当成替代方案。
- 未来接入内部 Git 服务时，`git_clone` 可作为新的 `source`（ADR-0013 已预留），
  不改变工作区模型。

## 复核

- **Verified by**：`pytest -m "not wsl and not llm" tests/unit/test_tenancy.py
  tests/unit/test_workspace_paths.py tests/unit/test_host_workspace_registrar.py`
  —— 分别锁定「每用户路径隔离」「工作区根含 tenant/owner」「host 只持 handle」。
- **Revisit when**：企业愿意把源码放到服务器并接受 Linux 基线；或单机容量
  不足需要多节点；或引入内部 Git 服务并希望以 `sandbox` 为协作基座。
