# ADR-0018：桌面桥只绑定本地页面与本地 origin

## 背景

桌面形态由 pywebview 承载页面，并向页面注入 `window.pywebview.api`。
当前桥能力包括：选择本机目录、在 VS Code 打开、复制工作区到 WSL、
生成/打开诊断包、检查/下载更新。这些能力都发生在用户本机，权限远高于
普通 Web API。

前后端分离后出现一个危险诱因：如果桌面壳改为加载远程前端，远程页面就会
直接获得本地桥。一次 XSS 或供应链污染即可升级为本机文件选择、任意目录
打开、更新下载等操作。即使页面本身由我们部署，也不应把"远程内容"和
"本地原生权限"放在同一个信任域。

约束：

- A2L/宿主能力必须保持最小权限与本地可见性（ADR-0015、T4）；
- A2 不持有 host 绝对路径，路径只在客户端解析；
- 更新与诊断涉及本机执行/数据外带，不能由服务端静默触发；
- 浏览器回退模式必须在不具备桥的情况下可用（功能降级）。

可选方案：

1. 远程前端直接在带 `js_api` 的 webview 中加载；
2. 远程前端加载到无桥 webview，原生操作另走本地代理；
3. 桌面继续加载本地前端包 + loopback API，桥只对本地页面开放；
4. 取消桥，所有原生操作改为本机常驻服务。

## 决策

**采用方案 3：桌面壳只加载本地前端包，桥只绑定本地 origin，并对每次调用
做 origin、顶层窗口与能力校验。**

1. **加载边界。**
   桌面页面与 API 都来自本地（`127.0.0.1` 或等价的本地静态服务），保持
   同源；不加载远程 URL。远程前端只存在于浏览器/BFF 形态。

2. **origin 与调用方校验。**
   桥的每个入口先校验当前页面 URL 的 origin 等于预期本地 origin，且调用
   来自顶层窗口；非顶层 iframe、非预期 origin、非本地 scheme 一律拒绝并
   写本地审计。

3. **能力保持窄面。**
   只保留目录选择、在编辑器打开、复制到 WSL、诊断、更新等具名操作；
   不提供"执行任意命令""读写任意文件""通用 shell/RPC"入口。路径参数必须
   规范化并限制在允许根目录内，符号链接与路径穿越按宿主策略拒绝。

4. **服务端二次判定。**
   `/api/capabilities` 返回 `desktop_mode` 等标志；桌面专属端点同时校验
   服务端模式与 loopback 来源。浏览器模式下这些端点返回 403，不能只靠
   前端隐藏按钮。

5. **危险操作本地确认。**
   更新、复制/覆盖、诊断包导出等操作需要用户可见确认；更新包必须验签，
   下载 URL 走允许列表，禁止页面静默安装。诊断包脱敏 token、密钥与用户路径。

6. **远程形态的替代路径。**
   如果将来必须使用远程前端，只能加载到**不带 `js_api`** 的 webview；
   原生能力改由本地受认证的 A2L/宿主代理提供，由用户本地授权，不能通过
   页面桥转发。任何"远程页面 + 本地桥"的组合都视为安全缺陷。

**否掉的替代**：远程页面直接带桥（信任域混淆）；把桥做成通用 RPC
（权限面失控）；因为"页面是我们自己的"而跳过 origin 校验（供应链/XSS
一旦发生就没有第二道防线）；取消桥并常驻系统服务（违背 ADR-0015 的
客户端生命周期约束）。

## 后果

### 好的

- 桌面原生能力与本地页面绑定，远程内容无法直接触达；
- 桥能力面保持窄，配合服务端 403 形成双保险；
- 更新/诊断的签名与脱敏要求明确；
- 浏览器形态的降级行为可预期。

### 坏的 / 代价

- 桌面与浏览器的功能矩阵长期存在差异，需要维护能力矩阵与降级提示；
- origin 校验、顶层窗口校验、路径校验都要逐方法实现并测试；
- 本地前端包需要打包、签名与升级流程；
- 远程前端若确有需求，需要额外开发本地代理，不能复用页面桥。

### 中性 / 需要留意

- 本地页面自身的 XSS 仍可能调用桥；桥只能靠窄能力、确认与路径限制降低影响，
  不能假设本地页面绝对可信；
- pywebview 的注入时机与 URL 获取方式需要在目标平台验证；
- 浏览器模式下"在编辑器打开"等功能不可用是设计选择，不是缺陷；
- 桥的审计日志必须落在 agent 不可写的位置，并与桌面诊断包隔离。

## 实现补充（2026-10-26）

- `launcher` 只把 loopback `control.url` 交给 pywebview，并把其 origin
  传给 `DesktopApi`；加载前再做一次 loopback 断言。
- `DesktopApi` 所有公开方法先校验 `window.get_current_url()` 的 origin
  精确匹配；无 window、非 http(s) 或 origin 不符时 fail closed。
- 前端包装 `window.pywebview.api`，非顶层窗口调用直接拒绝。
- 浏览器模式的 `/api/desktop/*` 返回 403 `desktop.unavailable`。
- 更新仍只打开下载页、不自动下载/安装；诊断包继续脱敏。

## 复核

- **Verified by**：设计契约见
  [RFC-0003](../rfc/0003-frontend-backend-separation.md)；实现后由
  `REQ-210` 的验收项与桌面手工清单覆盖远程 URL 拒绝、非预期 origin 拒绝、
  浏览器模式 403 与更新验签。
- **Revisit when**：需要远程桌面 UI、多窗口/多租户桌面、企业设备管理，
  或桥能力扩展到执行/安装类操作。
